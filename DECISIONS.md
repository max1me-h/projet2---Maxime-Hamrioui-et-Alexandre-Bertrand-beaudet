# Fiche de décisions

Une ligne par choix important. La dernière colonne est à remplir après chaque validation avec
l'auxiliaire (A : domaine, B : jeu de données, C : cible/métrique/modèle, D : interface).

| Choix | Options envisagées | Choix retenu et justification | Validé par l'auxiliaire (date) |
|---|---|---|---|
| Domaine (A) | Immobilier (données Jadco, déjà explorées) ; ressources humaines | **Ressources humaines.** Question concrète : quels aspects de la vie d'un employé sont liés à son départ ? Les données Jadco étaient confidentielles, incompatibles avec un dépôt public. Domaine sensible (emploi) : avertissement obligatoire dans l'interface. | À valider (A) |
| Jeu de données (B) | IBM HR Analytics (Kaggle) ; autres jeux RH Kaggle | **IBM HR Analytics.** 1470 lignes (entre 500 et 50 000), 26 caractéristiques numériques et catégorielles, cible claire. Licence ODbL / DbCL (vérifiée via l'API Kaggle : redistribution permise avec attribution). Employés fictifs, aucune donnée personnelle. | À valider (B) |
| Cible | Satisfaction au travail (1 à 4) ; satisfaction ≥ 3 ; indice moyen des 4 satisfactions (régression) ; départ (`Attrition`) | **Départ.** Nous voulions prédire la satisfaction, mais elle n'est liée à aucune autre variable (corrélations < 0,11). En validation croisée, aucun modèle ne bat la référence : 4 classes 27-29 % contre 31 % ; « satisfait » 60 % contre 61 % ; indice moyen R² ≈ 0. Sur le test, la régression logistique obtient 44 % d'exactitude équilibrée contre 50 % pour la référence. Le départ est la conséquence observable du contentement, et il est prévisible (les 4 satisfactions servent d'entrées). | À valider (C) |
| Métrique (C) | Exactitude ; F1 ; AUC ; exactitude équilibrée | **Exactitude équilibrée.** Avec 16 % de départs, l'exactitude récompense un modèle qui répond toujours « reste » (84 %). L'exactitude équilibrée vaut 50 % pour tout modèle constant : facile à expliquer à un non-informaticien (« 50 % = hasard »). F1, rappel et AUC sont affichés en complément. | À valider (C) |
| Modèle (C) | Régression logistique ; forêt aléatoire ; k plus proches voisins | **Régression logistique** (classes pondérées), comparée à une forêt aléatoire. Choix fait par validation croisée sur l'entraînement : 75,6 % contre 73,8 %. Sur le test, la forêt fait 73,5 % contre 72,5 %, un écart inférieur à l'incertitude (± 3 points avec 59 départs). Nous gardons le choix fait sans regarder le test. La logistique est aussi plus simple à expliquer et s'entraîne en 0,03 s. | À valider (C) |
| Pondération des classes | Aucune pondération + seuil ajusté ; `class_weight="balanced"` | **`class_weight="balanced"`**, seuil 50 %. Sans pondération, le modèle prédit presque toujours « reste ». Conséquence assumée : le « risque » affiché est un indice, pas une fréquence réelle (expliqué dans l'onglet « À propos »). | — |
| Colonnes retirées | Tout garder ; retirer les colonnes inutiles | **8 colonnes retirées :** 3 constantes, l'identifiant, 3 « taux » sans lien avec le salaire (r ≤ 0,03, probablement du bruit, et déroutants pour l'utilisateur), et le genre : motif de discrimination interdit, apport mesuré négligeable (< 1 point). L'âge et l'état civil sont gardés, car ils portent de l'information, et signalés dans l'avertissement. | — |
| Valeurs aberrantes | Les retirer ; les conserver | **Conservées.** Les valeurs hors 1,5 × EIQ sont des hauts salaires et de longues carrières, plausibles. Aucune valeur manquante ni aucun doublon dans le fichier. Le code les gère quand même (testé sur un fichier « sale »). | — |
| Champs vides et précision attendue | Exiger tous les champs ; remplacer un champ vide par la médiane ; un modèle par combinaison de champs ; moyenne sur des employés de référence | **Moyenne sur 40 employés de référence.** Exiger 26 champs décourage l'utilisateur. La médiane bloquait la précision à 50 % avec peu de champs (l'employé médian reste sous le seuil). Un modèle par combinaison de champs est impossible (2²⁶ combinaisons) et obligerait à réentraîner pendant l'utilisation. La précision attendue est mesurée sur le test avec exactement les mêmes champs : c'est honnête et sans réentraînement. | — |
| Technologie d'interface (D) | Tkinter ; Streamlit ; PySide | **Tkinter + ttk.** Inclus avec Python (rien à installer), fonctionne hors ligne, et Matplotlib s'y intègre (`FigureCanvasTkAgg`). Thème « clam » pour pouvoir colorer en rouge les champs invalides. | À valider (D) |
| Organisation de l'interface | Une seule page ; onglets | **4 onglets** (Prédiction, Le modèle, Historique, À propos). Le formulaire est construit à partir des métadonnées JSON, en 5 sections. Un bandeau d'avertissement reste toujours visible. | À valider (D) |
| Validation des saisies | Message à la première erreur ; toutes les erreurs d'un coup | **Toutes les erreurs d'un coup** (`SaisieInvalideError` réunit un message par champ), champs en rouge. Règles de cohérence entre champs, vraies pour les 1470 employés (ex. années dans l'entreprise ≤ expérience totale). | — |
| Séparation et reproductibilité | 80/20 ; 75/25 | **75/25 stratifié, graine 42** : 59 départs dans le test au lieu de 47 avec 80/20, pour une mesure un peu moins bruitée. | — |
| Versions des bibliothèques | Versions minimales ; versions exactes | **Versions exactes** dans `requirements.txt` : un modèle joblib n'est garanti relisible qu'avec la même version de scikit-learn. | — |
